# 地表路线与点位预览

2026-11-03。状态：基础算法已实现；游戏数据导入、玩家通行验证、World 接入尚未完成。

## 已验证的现状

- endfield-noclip 与 Atlos 固定的 viewer 版本均为 `1d8af42`。当前 pointPose 在首个可行高度比较 16 个方向，以遮挡数为主，以固定斜角为次；同分保留先遍历的方向。这解释了西南偏好，不代表该方向是来路。
- 当前 navigation companion 是区域/层级切换数据，不是步行路网。
- AKEData 的 NavMeshStateContainer 是导航块与场景状态的关联，LunaArea 是区域修改数据；两者都不能独立构建完整路网。
- 已通过现有 extractor 从当前安装读取 Unity class 238 NavMeshData，确认导航块资产实际存在，且包含 m_NavMeshTiles 和构建配置。一个 map01 状态块样本的代理半径约 0.41 m、高度 2.1 m、坡度 45°、台阶约 0.39 m。这是该样本的烘焙配置，不是经验证的玩家能力。
- AKEData 的 C# 导出方法体为空，只能作为接口结构证据。不能据此宣称还原了怪物完整算法。Unity 官方的通路搜索与局部避障分层可作实现参考：https://docs.unity.cn/2022.2/Documentation/Manual/nav-InnerWorkings.html
- AirWallRuntimeConfig 不是空气墙几何。空气墙几何、启用条件与关卡脚本仍需绑定到实际当前资源；查不到资产名不代表不存在空气墙。

## 统一规则

先得到可通行路线，再从路线求来路和预览视角。相机本身可以在空中或悬崖外；玩家路线必须贴在可通行地表，两者不能使用同一个“可达”判定。

有玩家起点时，使用玩家所在表面到目标交互表面的路线。没有玩家位置的静态预览不能声称有唯一最佳路线：应从同一可达分量内的传送点、道路入口等有来源的入口计算候选，保留不同进入方向。禁止用 level 中心方向推断来路。

用户已确认：沿来路越过目标的外侧放置相机，斜向回看，目标在前景、来路在背景。以末段约 12 m 的水平行进方向为参考，优先尝试左右 30° 和 45°。这些距离与角度是初始设计参数，尚未经过实景调优。纯垂直移动、过短路线、回折抵消时不猜方向。

候选排序先满足目标可见、镜头净空与已有门/破坏物约束，再考虑路线在画面中的连续可见长度、终点附近转角和地标。不能仅以方位夹角替换遮挡判断；路线在目标背后却被岩壁遮住仍不是好预览。无合格候选则保留原有回退，并明确未确认。

## 数据与仓库责任

1. endfield-noclip extractor：解码真实导航 tile、多边形、邻接/跨块 portal、离网连接、代理配置与坐标变换。验证版本、数组界限、索引和块边界，不能将未知字节布局猜成标准 Detour。
2. 同一导出过程加入碰撞体/空气墙和当前状态条件。导航块、门、桥、空气墙必须使用同一状态快照；未知条件禁止生成确认路线。只用可见渲染网格不能证明玩家可通行。
3. Ganglia：地表投影、通路规划、路线末段分析和动画采样。第一版仅步行；跳跃、攀爬、单向落差和滑索需明确的连接、方向、能力与状态条件。
4. Atlos World：起点选择、路线显示与播放；viewer 继续负责视线/镜头碰撞、场景状态与渲染。路线变化不能自动修改用户的世界状态。

数据发布需绑定 game build、scene、package generation、状态与代理配置。路线和预览缓存还要包含导航版本、起终点表面与配置。新数据完成前不提升现有 framing version，避免让所有点位丢弃已烘焙视角却得不到真正的新规则。

## 已实现的基础接口

`src/routes.mjs` 为无依赖 ES module，供离线与浏览器共用。

- `route(graph, start, goal)`：输入已验证的有向通路图。边含端点、连续折线、非负秒成本和 open/closed/unknown。只搜索 open 边；输出图上的最低成本路线，或 unmapped / no-verified-route。后者不代表游戏世界绝对不可达。
- `sampleRoute(points, meters)`：按三维弧长采样，夹紧端点，不使用会穿墙的自由样条。它是路线播放位置，不是自动相机姿态。
- `arrivalViews(points, options)`：根据末段来路生成远端斜视候选，尚需 viewer 检查可见性与构图。

当前 Dijkstra 使用线性候选集，适用于验证基础图，不适用于全世界大图性能验收。后续在真实导入数据规模明确后改堆/分层搜索；使用 A* 时启发式必须是旅行成本下界，不能让自定义成本破坏最优性。当前最优性仅限输入离散图，不声称连续空间最短路；多边形 corridor + funnel 是导入层就绪后的路线几何步骤。

## 验收顺序

1. 在 `0TpWNzY` 所在地表绘制真实可走网格，确认东侧路径确实连通到交互位置，排除附近低层、峡谷和空气墙。
2. 从东侧三个不同地表起点规划，检查末段一致性及图2方向的构图；从不连通平台起点返回无确认路线。
3. 检验门开关、桥未建/已建、空气墙启用/解除，以及相同 XZ 的不同高度。
4. 对路线采样检查每点和每段仍位于相应 corridor，状态改变后立即使旧路线失效。
5. 实景比较自由点位、狭窄入口、箱内点、洞穴、开放平原与多入口点。确认门/破坏物预览没有回归。
6. 完成后更新 framing/cache key，单点烘焙回归，再全量烘焙、更新 Atlos 的 submodule 与本地数据引用。远端发布需单独授权。
